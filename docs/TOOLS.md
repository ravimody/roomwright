# Tools

Generated by `tools/make_docs.py` from each tool's docstring; edit the tool, not this file.
Run them from inside `rooms/<room>/` as `uv run ../../tools/<tool>.py …` (engine checkout) or `roomwright <tool> …` (installed).

## Set up and check

### doctor.py

```text
Check that this machine can run the pipeline, and say how to fix what's missing.

Usage (from the repo root or any room folder):
  uv run tools/doctor.py            quick checks (seconds)
  uv run tools/doctor.py --full     also installs and imports Blender's Python module (bpy 4.5, ~400 MB on first run)

Checks: uv, git, Git LFS (installed, and scans/textures pulled rather than pointer files), Node (layout checker and
editor tests), Python 3.11 for bpy, optional Chrome (PDF export), optional Modal (cloud renders). Inside a coding
agent's sandbox it also checks what the sandbox blocks: writing uv's cache, the network for first-run downloads, and
(with --full) whether Blender starts at all. docs/AGENT_SETUP.md has the per-agent setup.
```

### new_room.sh

```text
First pass for a new room, from a phone scan to a draft room.json, a draft furniture list and review images.

  tools/new_room.sh <room-name> [path/to/scan.glb]

Without a scan it only creates rooms/<room>/ from the template: fill room.json from tape measurements (COOKBOOK,
"Without a scan"); the scan checks are skipped and reports say so.

Steps (each is also runnable on its own; see COOKBOOK.md section 2):
  1. rooms/<room>/ from rooms/_template/, scan copied to scan/scan_raw.glb
  2. align_and_render.py   -> scan/scan_aligned.glb, scan/alignment.json, renders/plan_cut*.png, elev_*.png
  3. map_room.py           -> renders/map/room_draft.json (+ review.png, ceiling.png)
  4. room.json seeded from the draft (outline, ceiling, scan transform, candidate openings) if still the template
  5. room_views.py         -> renders/views/plan.png + elev_*.png in room coordinates (read doors/windows here)
  6. detect_furniture.py   -> renders/map/furniture_draft.json + furniture.png (one footprint per piece)
Then by hand: doors/windows/fixtures in room.json, map furniture blobs to catalog types, cameras, style.
```

### validate_room.py

```text
Check a room's data before rendering: room.json, catalog.json, layouts/, render_sets/ and report/build.json against
the JSON Schemas in schema/, plus the checks a schema can't express (a door that isn't on a wall is silently dropped by
the renderer, a layout item whose type no catalog defines renders as a grey box, a render set naming a missing camera).

Usage:
  uv run ../../tools/validate_room.py            (from inside rooms/<room>/)
  uv run tools/validate_room.py --all            (from the repo root: every room, plus the shared and household catalogs)

Prints ERROR and WARN lines; exits 1 if there is any error.
```

### smoke_rooms.py

```text
Stress-test the engine on every room: run each pipeline step that applies to a room and summarise pass/fail,
timings and the key numbers (validation errors, layout issues, geometry agreement, render brightness).

Usage (from the repo root, or anywhere with a rooms/ folder):
  uv run tools/smoke_rooms.py [room ...] [--fast] [--layout as-scanned] [--out smoke.md]

Steps per room (skipped when they don't apply):
  validate      tools/validate_room.py
  layouts       tools/check_layout.mjs on every layout (errors are reported, not failures: proposals can break rules)
  flow          tools/flow_plan.py <layout> when room.json has "flow"
  speakers      tools/speaker_plan.py <layout> when the layout has "listening"
  geometry      tools/geometry_check.py <layout> (Blender; skipped with --fast): worst view agreement
  render        tools/render_photoreal.py <layout>, first camera, 4 samples, 240 px (Blender; skipped with --fast)
Outputs go to each room's renders/_smoke/ (git-ignored), so tracked files stay untouched. Writes a Markdown table to --out (default: stdout only) and exits 1 if any step failed.
```

## Align and map the scan

### align_and_render.py

```text
Headless Blender: import scan, align walls to axes, floor to z=0, export aligned GLB, render plan + elevations.

Usage: uv run ../../tools/align_and_render.py [--] <in.glb> <out_dir>   (multi-mesh scans are joined first)
```

### map_room.py

```text
Automatically map a room from its aligned scan: outline, ceiling levels, openings. Clutter-robust.

Run from inside rooms/<room>/ after align_and_render.py (needs scan/scan_aligned.glb, scan/alignment.json):
  uv run ../../tools/map_room.py [--seed X Y] [--cell 0.05] [--out renders/map]

Writes:
  renders/map/room_draft.json   draft room.json (outline, wallHeight, ceiling, openings, scan transform)
  renders/map/review.png        plan of the scan with the detected outline, walls and openings overlaid
  renders/map/ceiling.png       ceiling height map with detected levels

Strategy:
  * Furniture and clutter live below ~1.6 m, so nothing below that height is used for the outline.
  * The ceiling is the cleanest surface: cast rays straight up on a grid (catches slanted ceilings too).
  * Neighbouring rooms seen through openings also have ceiling; they are cut off by the strip of wall
    between door-head height and the ceiling (headers/soffits), found as vertical surfaces in that band.
  * Wall positions are refined from profiles just under the ceiling (ceiling - 0.33 to - 0.13 m, below crown
    moulding): real walls reach that band; bookcases and cabinets don't.
  * Openings are gaps in the mid-height walls; their head is the lowest surface above 1.5 m inside the wall
    thickness (the header).
```

### room_views.py

```text
Gridded review views of any room's scan, in room coordinates: plan (cut at 1.2 m) + one elevation per side.

Run from inside rooms/<room>/:
  uv run ../../tools/room_views.py

Uses room.json if present, else renders/map/room_draft.json (from map_room.py), for the room origin and extents.
Writes renders/views/{plan,elev_north,elev_south,elev_east,elev_west}.png with a 0.5 m grid labelled in
room coordinates, so positions of doors, windows, soffits and fixtures can be read straight off.
```

### detect_furniture.py

```text
Find furniture in a room scan and write a draft layout: one footprint per piece, with size, rotation and height.

Run from inside rooms/<room>/ after map_room.py and once room.json has the outline and scan.alignedOrigin:
  uv run ../../tools/detect_furniture.py [--min-area 0.04] [--wall-band 0.06]

Writes:
  renders/map/furniture_draft.json   {"items": [{id, x, y, w, d, h, rot, area}]} in room coordinates
  renders/map/furniture.png          plan of the scan with the detected footprints and their sizes

How it works: everything between 0.12 m and 1.9 m above the floor (furniture, not floor or ceiling) is rasterised
into an occupancy grid inside the room outline, minus a thin band along the walls (wallpaper, baseboards,
radiators). Connected blobs are pieces; each gets its minimum rotated rectangle and its tallest point. Tables
read as their top plus chairs, so expect to merge or split a few by eye. This replaces tracing every piece by
hand from the plan render: map each blob to a catalog type and adjust.
```

### sections.py

```text
Horizontal cross-sections of the whole scan (room frame, 0.25 m grid) to read wall lines and item footprints.

Run from inside rooms/<room>/:
  uv run ../../tools/sections.py [--heights 0.15,0.6,1.2,<ceiling-0.3>] [--out renders/sections.png]

The canvas covers the room outline plus 0.5 m (to show what the scan saw through openings). Default heights: floor
clutter, seat, counter height, and just under the lowest ceiling level (above most furniture, below crown moulding).
```

### region_sections.py

```text
Zoomed cross-sections of one room region: horizontal cuts at several heights plus two vertical cuts.

Run from inside rooms/<room>/:
  uv run ../../tools/region_sections.py x0 y0 x1 y1 out.png [xcut] [ycut] [--heights 0.3,1.0,...]

Default cut heights run from 0.3 m to just under the region's ceiling (from room.json, slopes included); the vertical
cuts (at xcut, looking east, and ycut, looking north; default the region's centre lines) reach 0.2 m above the
highest ceiling in the region, so soffits, crown and slopes show.
```

### wall_profile.py

```text
Depth profile along one wall: horizontal rays cast outward from just inside the wall, every 5 cm along it, at
several heights. Prints how far past the wall line each ray hits (metres, + = beyond the wall, - = in front of it).

Reading it: a run of large or "inf" values that stops at a header height is a doorway or opening (its width and
head height come straight off the table); a run a few cm proud of the wall is a closed door, a roller shade or a
picture; "inf" low down only is usually furniture against the wall hiding it. The wall line at each position is
the outline edge facing that way (so stepped walls and bays are measured from their own face), else the outline's
bounding box. The ten probe heights run from 0.3 m to just under the lowest ceiling along the probed stretch
(room.json, slopes included), so a sloped or low ceiling doesn't read as an opening; set them with --heights.

Usage (from inside rooms/<room>/):
  uv run ../../tools/wall_profile.py <north|south|east|west> [from to] [--inset 0.15] [--heights 0.3,0.9,...]
```

### corner_views.py

```text
Perspective close-ups of the aligned scan (textured, flat light), to look at a corner, a soffit or an opening.

Usage, from inside rooms/<room>/:
  uv run ../../tools/corner_views.py "<shot>;<shot>..." [--lens 18] [--res 1400x1000]

A shot is either the name of a room.json camera (its own lens and roll are used) or an ad-hoc view
"name:ex,ey,ez:tx,ty,tz" (eye and target in room coordinates: x east, y north, z up; --lens applies).
Writes renders/corner_<name>.png.
```

### ceiling_views.py

```text
Reflected ceiling plan of the aligned scan: the textured ceiling seen from below (everything above --cut), drawn
north-up and east-right like a plan, cropped to the room with a 0.5 m grid labelled in room coordinates. Use it to
find recessed cans (bright spots), beams, soffits and vents.

Usage, from inside rooms/<room>/:
  uv run ../../tools/ceiling_views.py [--cut 1.45] [--px 150] [--pad 0.3]

Writes renders/ceiling_up.png.
```

### ceiling_compare.py

```text
Ceiling check: how well room.json's ceiling (top, downstands, slopes) matches the scan, on a 5 cm grid.

Run from inside rooms/<room>/:
  uv run ../../tools/ceiling_compare.py [--layout as-scanned] [--step 0.05] [--out renders/ceiling_check]

For every grid cell inside the outline it casts a ray straight up from 0.5 m below the modelled ceiling and records the
first scan hit, so sloped ceilings, soffits and stair undersides are all measured (normal-filtered sampling drops
slopes). Cells under layout items that reach within 0.5 m of the ceiling (wardrobes, a sauna, ceiling fans, chandeliers)
are left out, as are scan holes and the ring of cells along the walls (wall faces, crown moulding). Prints the share of cells within 3 cm and 5 cm, then every mismatch region over
0.04 m2 (where, how big, scan higher or lower), which is what to fix or explain. Target: > 90% within 3 cm.

Writes <out>.png (scan | model | difference, same colour scale, north up, 1 m grid) and <out>.json (grid origin and
step, stats, regions, and the measured heights as rows south to north).
```

## Verify the model

### geometry_check.py

```text
Geometry check: where does the model (room.json shell + a layout's furniture) disagree with the 3D scan?

Builds the model and loads the aligned scan into one Blender scene (room frame), then:
  * views: for every room.json camera, casts a ray through every few pixels into the model and into the scan and
    compares the depths. Red = the model has a surface in front of where the scan's is (something modelled that
    isn't there, too big, or misplaced); blue = the scan has a surface in front of the model's (something real that
    the model lacks, is too small or misplaced). Grey = the scan has a hole there (glass, mirror, unscanned), not
    judged. Fast flat (Workbench) renders of scan and model sit next to the overlay.
  * plan: a top-down height map on a 4 cm grid (rays down from 2 m or just under the ceiling): the most direct check
    of furniture footprints and heights.
  * report: every layout item and shell part ranked by how much of it disagrees, plus clusters of scan geometry
    that no item explains (unmodelled furniture or clutter).
Not judged: the shell's "beyond_*" stand-ins for neighbouring rooms, and items whose catalog entry says
"scanVisible": false (glass, crystal, thin wire: LiDAR sees the wall behind them). Glass parts of items (a sauna door,
a glass table top: any Principled material with transmission >= 0.5) are see-through for the rays, so what's behind
them is judged, as the scanner saw it; the shell's windows are not. Fan blades, thin poles and soft
clutter (pillows, throws) also disagree by nature; read their flags with that in mind.

Usage, from inside rooms/<room>/:
  uv run ../../tools/geometry_check.py <layout> \
      [--views a,b] [--tol 0.12] [--res 700x440] [--step 4] [--cell 0.04] [--out dir]

Writes renders/geometry_check/<layout>/{view_<name>.jpg, plan.png, report.txt, report.json}. Not photoreal and
needs no lighting: run it after every geometry or layout change, before any photoreal set.
```

### photo_match.py

```text
Recover the camera of a real photo of the room, so model renders can be compared 1:1 with it.

Renders the textured scan (flat Workbench, fast) from a candidate camera at low resolution, scores how well its edges
line up with the photo's, and searches the camera's position and aim (yaw, pitch, roll) from a rough starting guess.
The focal length comes from the photo: its 35 mm-equivalent (EXIF FocalLengthIn35mmFilm, read automatically; or pass
--f35) is converted for the photo's aspect (Blender lens = f35 x 1.04 for 4:3, 1.00 for 3:2, 0.955 for 16:9; 36 mm
sensor across the long side). Edges, not colours, are compared, so night photos with mixed light still match the
flat-lit scan. Photos may be JPEG, PNG or HEIC.

Usage, from inside rooms/<room>/:
  uv run ../../tools/photo_match.py <photo> --eye x,y,z --target x,y,z [--f35 24] [--points landmarks.json]
      [--fit-lens] [--name n] [--iters 400] [--out renders/photo_match]

Writes <out>/<name>.json ({"eye", "target", "lens", "roll", "score", "portrait"}) and <out>/<name>_overlay.jpg (photo,
scan from the found camera, and a blend) to check by eye. Copy eye/target/lens/roll into a room.json camera entry:
render_photoreal, scan_compare and geometry_check all apply roll the same way (roomframe.apply_camera). A wrong start
can lock onto a similar-looking wall: check the overlay.
```

```text
Writes <out>/<photo-stem>.jpg per camera and <out>/all.jpg (every sheet stacked).
```

### color_match.py

```text
Calibrate colour and light against real photos whose cameras are known (room.json `cameras`, e.g. recovered with
tools/photo_match.py).

For each camera it renders the layout from that camera exactly as render_photoreal.py would (low resolution), plus
passes that label every pixel by part (wall, ceiling, floor, trim, baseboard, or a layout item and its material) and
give each part's albedo. It then compares each part's median colour with the photo's (masks eroded to skip edges;
pixels that disagree wildly, e.g. moved furniture, a TV picture or a person, are dropped), and:

1. fits the scene's exposure, white balance and tint (Blender's own colour management) to the parts whose colour is
   trusted (paint: walls, ceiling, doors and trim, baseboards by default), and
2. for every part, finds the albedo that would reproduce the photo under the model's lighting, as a suggested hex for
   room.json `materials` or the item's catalog colour.

A part's colour in a photo is albedo x light, so a suggestion is only as good as the model's lighting there: trust
suggestions that agree across several photos and daylight photos more than night ones. Emitters (lamp shades, sky
panels) are reported but get no suggestion; their difference says the lamp is brighter, dimmer, warmer or cooler.

Usage, from inside rooms/<room>/:
  uv run ../../tools/color_match.py <layout> <camera>[=<photo>] [...] [--lighting <scene>] [--samples 32] [--width 480]
      [--trust wall,ceiling,door,baseboard] [--out renders/color_match]

The photo comes from `camera=path` or the camera's "photo" key in room.json. HEIC photos are read with pillow-heif
(or macOS `sips`). Writes <out>/<camera>.json and <camera>.jpg (photo | render as set up |
render with the fitted exposure and white balance | per-part swatches) and, for several cameras, <out>/summary.json
with the median exposure and white balance and, per part, whether the photos agree (CONSISTENT) on a new colour.
```

### light_match.py

```text
Calibrate the lights against real photos whose cameras are known (room.json `cameras` with a `photo`, e.g. from
tools/photo_match.py): how bright and how warm each light really is.

It renders each camera as render_photoreal.py would, with every light in its own Cycles light group (daylight, the
cans, each lamp type, the fire, accents, an item's interior light, each lit screen), so the image is a sum of one
image per group. Light transport is linear and per channel, so any lumens and colour temperature per group can be
tried without rendering again. It then fits, on the parts whose colour is known (paint: walls, ceiling, doors and
trim, baseboards; --trust), each split into image tiles (--tiles) because how the light falls across a wall is what
tells two lights apart:

- one intensity scale per group (actual / modelled light),
- the colour temperature of each group, relative to the brightest one (with a single light, its colour and the
  camera's white balance can't be told apart, so it stays as in the data), and the colour of lit screens,
- the photo's white balance,

with the camera's exposure taken from the photo's EXIF (shutter, aperture, ISO -> EV100). Phones process photos
(tone curves, Night mode and HDR merges, a bright TV in the frame), so absolute levels are weak evidence: results
are reported relative to an anchor group whose lumens come from data (--anchor), and the anchor's own scale is the
"camera offset" (the phone, or every light dimmer than modelled: photos alone can't tell which). A value is
CONSISTENT when two thirds of the photos agree within --max-spread stops (or --max-kelvin-spread). --write puts
consistent results into the room's data: lumens and kelvin (catalog `light`, or the layout's items with
--to layout; room.json `lights.cans`; a fixture's `fire` or `screen`), `daylight.scale`, the scene's dimmer
settings for dimmed lamps, its white balance, and the camera offset as its `exposureBias` (for `exposure: photo`).
--absolute writes every group's own scale instead.

Usage, from inside rooms/<room>/:
  uv run ../../tools/light_match.py <layout> <camera>[=<photo>] [...] --lighting <scene> [--samples 32]
      [--width 400] [--tiles 4] [--trust wall,ceiling,door,baseboard] [--min-share 0.03] [--max-spread 0.6]
      [--anchor GROUP] [--absolute] [--resummarise] [--write [--to catalog|layout]]

Writes renders/light_match/<camera>.json and .jpg (photo | model as set up | model fitted) and summary.json.
```

### flow_plan.py

```text
Flow & function plan: traffic paths, walkway widths at pinch points, and seating distances for a layout.

Run from inside rooms/<room>/:
  uv run ../../tools/flow_plan.py <layout> [--out renders/flow/<layout>.png] [--scale 150]

Paths and distances come from the layout's "flow" block, else room.json "flow":
  "flow": {
    "paths": [{"name": "Between the openings", "points": [[x, y], ...], "min": 0.9}],   # main paths >= 0.9 m (36 in)
    "distances": [{"a": "<item id>", "b": "<item id>", "label": "Sofa to sofa"}]
  }
Each path is sampled every 5 cm; at each sample the clear width perpendicular to the path is measured to the nearest
obstacle: the floor contact of the furniture (`baseW`/`baseD` when given, e.g. a speaker stand's plate), fixtures and
walls. Rugs and other `floorLayer` items, wall-mounted items above 1.2 m and ceiling-hung items don't count. The
narrowest point is marked and colour-coded: green >= target, orange within 15 cm of target, red below. A path that passes
through an obstacle or outside the room between free stretches is reported as blocked (width 0 at the first
blocked point); starting or ending at a piece of furniture (the seat it leads to) is fine. Writes a PNG and a
JSON summary next to it.
```

### speaker_plan.py

```text
Surround speaker placement check for a layout: angles, distances, heights and toe-in from the main seat, drawn on
the plan against the Dolby / ITU-R BS.775 targets.

The layout needs `"listening": {"x", "y", "ear", "facing": [dx, dy]}` (main seat, ear height, the direction the
listener faces) and `"channel"` on each speaker item: FL FR C SL SR SBL SBR SW1 SW2. A speaker's catalog entry may give
`channelHeight` (driver/tweeter centre above the speaker's base); otherwise the box centre is used.

  uv run ../../tools/speaker_plan.py <layout> [--out renders/speakers/<layout>.png]     (from inside rooms/<room>/)

Prints a table and writes the plan image plus <out>.json.
```

## Render

### render_photoreal.py

```text
Photoreal Cycles renders of a layout.

Usage, from inside rooms/<room>/:
  uv run ../../tools/render_photoreal.py <layout> [--lighting day|night|evening|standard|<scene>] (default standard) [--views v1,v2]
      [--samples 48] [--res 1400x875] [--tag folder] [--exposure stops] [--white-balance K] [--meter-layout L]

Writes renders/photoreal/<tag or layout>/<view>.png (render_batch.py and render_modal.py name folders
<tag>, or <tag or layout>-<lighting> when several lightings are rendered). Geometry comes from room.json
(tools/blender_scene.py) and the layout; furniture from the catalogs via tools/blender_models.py. Lighting is a
base preset or a room.json "scenes" entry (see resolve_scene). Quick tests: --samples 16 --res 700x440.

Lights are physical (tools/photometry.py): fixtures in lumens and kelvin with their dimmer curve, daylight from a
sky model, and a camera that exposes and white-balances like a phone (or like the photo a camera was matched to).
Lights without data use stated defaults, printed as ASSUMED lines; fit them to photos with light_match.py.
Other tools render exactly the same scene with build() + aim() + expose() (e.g. color_match.py, light_match.py).
```

### render_batch.py

```text
Render several photoreal sets locally, one render_photoreal.py run per (layout, lighting).

Usage, from inside rooms/<room>/:
  uv run ../../tools/render_batch.py render_sets/<name>.json [--samples 48] [--res 1400x875] [--only tag1,tag2] [--show] [--dry-run]

The sets file is the same format as `modal run tools/render_modal.py --batch` (a list), so one file serves both:
  [{"layout": "proposal", "lighting": "day,evening", "views": "a,b", "tag": "zones"}, ...]
- "lighting" may list several scenes; each gets its own folder.
- Output folder: "tag" when one lighting is given, else "<tag or layout>-<lighting>" (as on Modal).
- "views" defaults to every camera in room.json; "samples"/"res" in a set override the command line.
- "room" is accepted (Modal needs it) and must match the current folder when present.
- "meterLayout": meter the auto exposure on another layout (e.g. today's), so a proposal renders at today's exposure
  and the difference shows (render_modal.py --batch does the same).
--show opens each finished folder in the system image viewer.
```

### render_modal.py

```text
Render photoreal views on Modal cloud GPUs, in parallel. Same output as tools/render_photoreal.py.

Run from the folder that holds rooms/ (the repo root) or from a room folder (then --room defaults to it):
  modal run tools/render_modal.py --room <room> --layout <layout> --lighting evening \
      --views <cam1>,<cam2> --samples 48 --res 1400x875 [--tag <folder>] [--gpu L4]

  # several lighting presets at once (each preset × each view is one GPU job):
  modal run tools/render_modal.py --room <room> --layout <layout> --lighting day,evening

  # many sets in one run: the same sets file as render_batch.py, plus "room" per set
  modal run tools/render_modal.py --batch rooms/<room>/render_sets/<name>.json
  roomwright render-modal …  (the same, with the engine installed as a package)

Each (lighting, view) pair runs in its own container. Results land in rooms/<room>/renders/photoreal/<folder>/<view>.png,
with the same folder naming as render_batch.py: <tag> when one lighting is given, else <tag or layout>-<lighting>.
(render_photoreal.py run directly writes <tag or layout>.) A set's "meterLayout", "samples" and "res" work as in
render_batch.py. Uploaded: the engine (tools/, shared/), the household's catalog.json, builders/, models/ and textures/,
and rooms/ without scans, photos, reports and renders (room.json, catalogs, builders, layouts, render sets, textures).
```

### photometry.py

```text
Photometric units for the renderer: real fixtures (lumens, kelvin, beam angle, dimmer setting), daylight (lux) and
cameras (EXIF exposure) to Blender/Cycles units, and back. No Blender import, so it is unit-tested and usable anywhere.

Conventions (measured in Cycles 4.5, see tests/test_photometry.py): a light's colour is normalised to luminance Y = 1
(linear Rec.709 / sRGB primaries, D65 white), and one Blender watt of such a light is 683 lumens (the photopic peak,
as in other physically based renderers). Cycles itself is plain radiometry: a point light of P W has intensity P/4π W/sr,
a spot light has the intensity of the point light of the same power (masked to its cone), an area light is Lambertian
(radiance P/(π·A)), a sun's strength is irradiance (W/m²), and a world or emission strength is radiance (W/m²/sr). So
scene-linear pixel values are luminance / 683 (cd/m²).

Usage: `uv run tools/photometry.py <kelvin>` prints the light colour, `... ev <t> <N> <ISO>` a photo's EV100 and the
render exposure that matches it.
```

## Models and textures

### model_import.py

```text
Turn a downloaded 3D model into a clean GLB for a catalog entry ("model": "glb", "file": "models/<name>.glb").

Imports GLB/glTF, OBJ, FBX, USD/USDZ, STL, PLY or DAE; keeps only the meshes (and their materials), optionally only
the objects whose names contain one of --only; converts units; turns it so its front faces -y (south at rot 0, the
engine's convention); sets it on the floor centred on its footprint; reduces it to a triangle budget; optionally scales
it to the product's real size; and writes one GLB. Prints the size before and after, and against --spec, so you can
check the model against the spec sheet before using it.

Usage (from the household folder, or a room folder for a room-only model):
  uv run tools/model_import.py <file> [--out models/<name>.glb] [--units auto|m|cm|mm|in] [--front -y|+y|-x|+x]
      [--rotate RX,RY,RZ] [--only NAME[,NAME]] [--fit W,D,H [--stretch]] [--spec W,D,H] [--max-tris 150000]
      [--max-texture 1024]

  --front     which way the model's front faces after import (glTF files from most sources: -y, the default)
  --rotate    extra rotation in degrees about x, y, z (e.g. 90,0,0 for a model lying on its back)
  --fit       scale to the product's size in metres (uniform, so it fits inside; --stretch: each axis exactly)
  --spec      compare with the product's size without scaling
Then add {"model": "glb", "file": "models/<name>.glb", "w": .., "d": .., "h": ..} to the catalog; the renderer and
the editor fit it to w x d x h again (catalog `fit`). Check licences first: docs/MODELING.md lists sources.
```

### rug_from_scan.py

```text
Recover a rug (or any floor covering) texture from the textured scan: top-down orthographic view with everything
above the rug clipped away, then fill the occluded parts using the rug's mirror symmetry.

Run from inside rooms/<room>/:
  uv run ../../tools/rug_from_scan.py snap x0 x1 y0 y1 [--clip 0.03] [--ppm 300]
      -> renders/rug/top_<x0>_<y0>_<x1>_<y1>.png: raw top-down of that room-coordinate rectangle, to find the rug's edges
  uv run ../../tools/rug_from_scan.py rug x0 x1 y0 y1 --out textures/rug-x.jpg [--sym xy|x|y|none]
        [--corners "x,y x,y x,y x,y"] [--size W,H]
      -> the rug rectangle, holes (under furniture) filled from the mirrored quadrants, then diffused.
         Phone scans drift, so a rug can come out as a slightly skewed quadrilateral: pass its corners in room coords
         (TL, TR, BR, BL as seen from above, north up) and its true size in metres to rectify it first.

Room coords as in room.json (x east, y north, metres). The scan is placed with room.json scan.alignedOrigin, as in
scan_compare.py. "Holes" are pixels where the clipped scan has no surface (magenta background) or where furniture
skirts survive the clip; the fill takes the first mirror image that is valid (x-flip, y-flip, both), so a 2-fold
symmetric medallion rug comes back almost whole. Whatever is still missing is filled by repeated blurring.
```

### rug_texture.py

```text
Procedural traditional-rug textures (whole rug, not a tile): borders with guard stripes, an optional medallion with
corner spandrels, an allover field motif, abrash (colour banding) and wool grain. For mock-ups of rug *types*, not

  uv run ../../tools/rug_texture.py <style> <W_m> <H_m> <out.jpg> [--ppm 300] [--seed 1]

Styles (palette + layout presets, tweak in STYLES): oushak, serapi, sultanabad, kazak, heriz.

```

### wallpaper_from_scan.py

```text
Capture a wall's wallpaper from the textured scan as a tileable image for renders.

Run from inside rooms/<room>/:
  uv run ../../tools/wallpaper_from_scan.py <wall: north|south|east|west> <from> <to> <z0> <z1> [out=textures/wallpaper.jpg]

<from>/<to> are positions along the wall in room coordinates (x for north/south walls, y for east/west), z0/z1 the
height band to keep (above the wainscot, below the crown). Pick a stretch with nothing in front of it. The scan is
rendered orthographically, square-on, with flat (emission-like) shading, so the image is the wall's own texture at
a known scale. The left and right edges are cross-faded so the image tiles with a soft seam.

Then in room.json: "materials": {"wall": {"texture": "textures/wallpaper.jpg", "width": <to-from>,
"wainscot": {"height": 0.9, "hex": "#F1EFEA"}}} and render_photoreal maps it onto every wall.
```

## Other

### fake_scan.py

```text
Make a stand-in phone scan from a room's model: for demos, tests and rooms whose real scan can't be shared.

Builds the shell from room.json and a layout's furniture (the same models the renders use), then makes it behave
like a LiDAR phone scan: one textured mesh, small per-point noise and slow drift across the room, holes where glass
is (windows, glazed doors) and in a patch of ceiling, and an arbitrary pose (turned about the vertical, floor below
the origin, as a phone app leaves it). The pipeline then treats it like any scan: align_and_render.py, map_room.py,
geometry_check.py, ceiling_compare.py, scan_compare.py and the editor's scan overlay all run on it.

Usage, from inside rooms/<room>/:
  uv run ../../tools/fake_scan.py <layout | path/to/layout.json> [--out scan/scan_raw.glb] [--seed 7]
      [--yaw 12.5] [--offset 1.3,-0.7,-1.15] [--noise 0.006] [--drift 0.015] [--hole x0,y0,x1,y1] [--edge 0.4] [--max-faces 3000]

The layout can hold things the room's own layouts leave out (a basket, a toy box): the geometry check then lists
them as scan blobs no item explains, as it would for real clutter. --hole (repeatable) removes the ceiling over a
rectangle in room coordinates (glossy or dark ceilings scan patchy); default: one 0.6 x 0.5 m patch.
```
